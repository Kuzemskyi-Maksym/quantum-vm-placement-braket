# Квантове розміщення ВМ — порівняння методів (AWS Braket)

Код для порівняння методів розв'язання задачі розміщення віртуальних машин (VM placement / consolidation),
сформульованої як QUBO/CQM, на спільних тестових інстансах, із запусками QAOA на реальному квантовому
залізі (IQM Garnet) через Amazon Braket. Продовження першої статті (QAOA + SLR).

Супровідні нотатки (контекст, рішення, журнал запусків) — в Obsidian-сховищі, не тут.

## Інстанси (`config.py`, змінна середовища `VMP_INSTANCE`)
| Назва | ВМ | ФС | Призначення |
|---|---|---|---|
| `full` (за замовч.) | `[3,4,2,5,3,4]` | `[12,12,12]` | інстанс першої статті; лише класичні методи (~33 кубіти зі slack) |
| `common` | `[6,5,2,1]` | `[12,12]` | спільний інстанс для всіх 5 методів; 10 кубітів у slack-free кодуванні |
| `W` | `[6,5,2,1]` | `[12,12,12]` | warm start / критерій міграцій; 15 кубітів; поточний розподіл `X0=[0,1,2,2]` |
| `L18` / `L21` / `L28` | `[8,5,3,1,1]` / `[9,3,2,2,1,1]` / `[9,9,4,3,2,1]` | 3×12 / 3×10 / 4×12 | більші інстанси для Emerald/Forte (18 / 21 / 28 кубітів), парні штрафи достатні |
| `large` | 30 ВМ (seed 7) | 12 × 20 | лише класичні (ГА vs BRKGA) |
| `rand` | `VMP_N` ВМ, `VMP_SEED` | `VMP_N` × 20 | випадкові великі інстанси, лише класичні |

Спільні параметри: поріг утилізації `T = 0.9`, множники штрафу `λ1 = λ2 = 6.0` (slack-free QAOA: `λ = 3`).

### Критерій з міграціями (рішення керівника, 2026-11-01)
Ціль: **F(x) = (активні ФС) + MU · Σ_j s_j·[ВМ j змінила сервер] / Σ_j s_j** — вартість переміщення
пропорційна розміру ВМ; другий член нормовано в [0, 1] (переселити всі ВМ коштує MU). `X0` — поточний
розподіл (`VMP_X0="0,1,2,2"`), `MU` — `VMP_MU` (за замовч. 1.0). Якщо `X0 = None`, F = кількість ФС, як раніше.
Для QUBO член міграцій — лише лінійні поля на кубітах x_{j,X0[j]}: нових кубітів не потрібно.
Реалізовано в `cp_sat.py` (точна ціль), `brkga.py` (фітнес + ключі «залишитись»), `warm_start_qaoa.py`.

## Методи
| Файл | Метод | Примітка |
|---|---|---|
| `mbfd.py` | MBFD (Modified Best Fit Decreasing) | жадібна евристика; міграцій не бачить — baseline «повна переукладка» |
| `cp_sat.py` | CP-SAT (Google OR-Tools) | точний еталон, з ціллю F (ФС + міграції) |
| `brkga.py` | **BRKGA** (Gonçalves & Resende) | основний ГА для порівнянь; декодер First Fit; у режимі міграцій 2N ключів |
| `genetic.py` | базовий ГА | лишено лише для `compare_ga.py` (на 30+ ВМ програє BRKGA) |
| `annealing.py` | SimulatedAnnealingSampler (`dwave-samplers`) | класична емуляція відпалу |
| `qaoa_noslack.py` | QAOA без slack-бітів, точна симуляція | парні штрафи місткості; 8–15 кубітів |
| `qaoa_noslack_noisy.py` | те саме з шумом (Aer): решітка або повна зв'язність | ілюстративні рівні помилок; режим `scaling` — C/L18/L21/L28, кути кешуються в `angles_*.json` |
| `qaoa_fast.py` | numba-ядра точної симуляції (холодний і теплий старт) | ~10× швидше за numpy на 15–21 кубіті, звіряються з `qaoa_exact` у тестах |
| `qaoa_noslack_real_qpu.py` | QAOA на IQM Garnet | режими `local` / `submit p shots` / `fetch <TaskID>` / `control p shots` |
| `warm_start_qaoa.py` | QAOA з теплим стартом із X0 | ціль «максимум P(кращий за x0)», член міграцій MU, змішувач за розміром ВМ (`--mixer size --alpha 2`) |
| `warm_start_noisy.py` | теплий старт з шумом (Aer, сітка 4×4) | чи виживає сигнал при CX ≈ 1–2% — перевірка перед платним прогоном |
| `placement_new.py` | **Алгоритм 2**: розміщення нових ВМ | Best Fit Decreasing на залишках, перебір, CP-SAT, QAOA лише над новими ВМ (кубіти не залежать від розміру ЦОД); режими `local`/`submit`/`control`/`fetch` для Braket |
| `lifecycle_sim.py` | симуляція життєвого циклу ЦОД | прибуття → алгоритм 2 → завершення → алгоритм 1 (none / повна переукладка / BRKGA з MU / CP-SAT з MU), тригери, усереднення по seed |
| `qaoa.py`, `qaoa_exact.py`, `qaoa_real_qpu.py`, `qaoa_fetch_result.py`, `qaoa_aer_control.py` | старе slack-кодування (16 кубітів) | лишено для відтворення перших прогонів |

`cqm_model.py` — CQM/BQM (dimod) для slack-кодування.

### Вибір QPU (`devices.py`)
`BRAKET_DEVICE=garnet` (20 кубітів, за замовч.) | `emerald` (IQM, 54 кубіти, той самий регіон, $0.0016/shot) |
`forte` (IonQ Forte-1, 36 кубітів, повна зв'язність, $0.08/shot — запитує підтвердження). Скрипти `qaoa_noslack_real_qpu.py`
і `warm_start_real_qpu.py` перед submit перевіряють статус, кількість кубітів і вікна доступності, друкують оцінку
вартості, а всі submit/fetch пишуть у журнал `qpu_runs.json`.

## Порівняльні скрипти
```powershell
python run_all.py                                              # 5 методів на full → results.json
$env:VMP_INSTANCE="common"; python compare_common.py           # 5 методів на common (ГА = BRKGA) → results_common.json
$env:VMP_INSTANCE="large";  python compare_ga.py               # базовий ГА vs BRKGA на великих інстансах
$env:VMP_INSTANCE="W";      python compare_migration.py        # ціль з міграціями, MU ∈ {0,0.5,1,2,5} → results_migration.json
$env:VMP_INSTANCE="W";      python warm_start_qaoa.py pbetter --mu 1 --mixer size --alpha 2
$env:VMP_INSTANCE="W";      python warm_start_noisy.py --mu 1 --mixer size --alpha 2   # шумна симуляція (Qiskit)
python placement_new.py --new 3,4                              # алгоритм 2 на прикладі (3 ФС, нові ВМ [3,4])
python lifecycle_sim.py --steps 20 --seeds 10                  # життєвий цикл (+ CP-SAT, тригери) → results_lifecycle.json
python placement_new.py local 2 --new 3,4,2                    # алгоритм 2: схема QAOA на локальному симуляторі Braket
python qaoa_noslack_noisy.py scaling                           # шум × топологія для C/L18/L21/L28 → results_noisy_scaling.json
$env:VMP_INSTANCE="W"; python compare_migration.py --random 10 --seed 1   # статистика по x0 → results_migration_random.json
python -m pytest -q                                            # тести конвенцій (-m "not slow" — швидкі)
$env:QAOA_INSTANCE="C";     python qaoa_noslack_real_qpu.py submit 2 1000   # платний запуск на Garnet
```
У `compare_migration.py` точний оптимум рахується ще й повним перебором (M^N розподілів), тому скрипт
працює і без OR-Tools.

## Встановлення
```bash
pip install -r requirements.txt
```
Версії зафіксовано в `requirements.txt` (з ними отримано результати). Для запусків на Braket потрібен
налаштований `aws configure`. Усі `results_*.json` мають спільний верхній рівень
`{"instance", "generated", "git", …}` (`config.save_results`).

## Результати (коротко)
- **Класичні методи** (CP-SAT, MBFD, BRKGA, відпал) на `full` і `common` знаходять оптимум; BRKGA — оптимум у
  всіх запусках і на 30–60 ВМ, де базовий ГА провалюється, а MBFD помиляється на 1 сервер.
- **Slack-free QAOA на IQM Garnet:** інстанс B (8 кубітів, p=2, 1000 shots) — 20.9% ± 1.3% оптимальних shots
  проти 1.6% випадково; контроль із випадковими кутами 1.9%. Інстанс C (10 кубітів) — 7.3% ± 0.8% проти 0.78%.
  Результати узгоджуються з шумною симуляцією при ефективній помилці CX ≈ 1–2%.
- **Warm-start QAOA (точна симуляція, інстанс W):** p=2 зі звичайним RX дає ≈6% shots, кращих за x0, і тяжіє до
  однієї дорогої міграції великої ВМ; змішувач, зважений за розміром ВМ (α=2), дає ≈12% і знаходить оптимум
  з двома дешевими міграціями. Класичний випадковий сусід на 1–2 міграції — 25–40%: на малому інстансі
  квантовий варіант не виграє (`results_migration.json`).
- **Випадкові x0 (W, 10 шт.):** warm QAOA p=2 зі зваженим змішувачем — 0.15 ± 0.06 кращих за x0 проти
  0.06 для RX і 0.30–0.35 для випадкового сусіда; BRKGA не досягає оптимуму на 4 з 10 x0 (обмеження декодера).
- **Алгоритм 2 (нові ВМ):** для 2 нових ВМ на 3 ФС QAOA потребує 7 кубітів замість 18 у повній задачі;
  p=3 дає 40% оптимальних проти 2.3% випадково (точна симуляція).
- **Шум і масштаб (симуляція):** C p=2 тримає 17% оптимальних при помилці CX 1%; на L18/L21 сигнал нижче
  порога 0.5% — див. «Масштабування з шумом».
- **Життєвий цикл (12 ФС, 20 кроків, 10 сценаріїв, класика):** див. розділ «Життєвий цикл» нижче.
- Застереження: інстанси іграшкові (8–15 кубітів); перевага квантового методу над класикою не заявляється.
  Рамка — здійсненність на NISQ-залізі та вплив шуму.

### Міграції: статистика по випадкових x0
`$env:VMP_INSTANCE="W"; python compare_migration.py --random 10 --seed 1` (`results_migration_random.json`):
10 випадкових допустимих x0 з 3 активними ФС (з 30 можливих), для кожного й кожного MU — точний оптимум
перебором, BRKGA ×20, випадковий сусід на d міграцій, warm-start QAOA (точна симуляція, 25 рестартів кутів).
Стовпчики — P(стан кращий за x0), середнє ± std по x0; останній — частка x0, де найкращий стан серед 1000 shots
= оптимум F. L18 у цьому режимі не запускали (час і пам'ять).

| MU | x0, які можна покращити | BRKGA: частка запусків з оптимумом | випадк. сусід d=1 | d=2 | QAOA p=1 size | p=2 size | p=2 rx | QAOA best@1000 = опт. (p=1 size / p=2 size / p=2 rx) |
|---|---|---|---|---|---|---|---|---|
| 0.5 | 10/10 | 0.600 ± 0.516 | 0.300 ± 0.043 | 0.351 ± 0.042 | 0.058 ± 0.040 | 0.153 ± 0.061 | 0.056 ± 0.006 | 100% / 100% / 60% |
| 1 | 10/10 | 0.600 ± 0.516 | 0.300 ± 0.043 | 0.351 ± 0.042 | 0.058 ± 0.040 | 0.154 ± 0.062 | 0.059 ± 0.006 | 100% / 100% / 60% |
| 2 | 10/10 | 0.600 ± 0.516 | 0.300 ± 0.043 | 0.171 ± 0.030 | 0.058 ± 0.040 | 0.157 ± 0.062 | 0.046 ± 0.001 | 100% / 100% / 60% |

Висновок: на W зважений за розміром змішувач стабільно кращий за RX (p=2: 0.15 проти 0.05–0.06, і оптимум серед
1000 shots для всіх x0 проти 60%), але класичний випадковий сусід на 1–2 міграції все одно дає 0.17–0.35.
BRKGA доходить до оптимуму лише на 6 з 10 x0 (на решті — 0 з 20 запусків): обмеження декодера, а не пошуку —
ВМ без прапорця «залишитись» іде First Fit на перший за індексом сервер, тож оптимум на кшталт
x0 = [1,2,1,0] → [1,2,1,1] (ВМ 3 переїжджає з ФС 0 на вже активний ФС 1) недосяжний, поки ФС 0 порожній.
Виправлення (для мігруючих ВМ спершу пробувати вже активні сервери) змінює старі результати — винесено в
«Наступні кроки».

### Масштабування з шумом
`python qaoa_noslack_noisy.py scaling` (`results_noisy_scaling.json`): холодний slack-free QAOA, кути — точна
numpy-оптимізація ⟨Ez⟩ (30 рестартів, кеш `angles_<інстанс>_p<p>.json`). Рівні шуму: деполяризація e1 на sx/x,
e2 на cx, readout ro (e2 = 0.3% — орієнтир Forte/Emerald за паспортами). Топологія `lattice` — квадратна решітка
r×c ≥ n (SWAP-и після транспіляції), `all` — повна зв'язність (як на іонах). Aer statevector, траєкторії з
усередненим вектором ймовірностей (800–2000 на рівень; 200 для L21 на решітці), readout застосовано точно.
Безшумний стовпчик збігається з точним numpy (≤ 0.01 п.п.). Для L28 (2^28 станів) і L21 p=2 на решітці симуляцію
не запускали — лише CX, глибина і оцінка точності схеми F = ∏(1−e)ⁿ за кількістю вентилів.

Висновок: сигнал обмежує глибина схеми, а не число кубітів. На C (10 кубітів) p=2 з 84 CX на решітці тримає
17.1% при e2 = 1% (у 22× вище випадкового), а на L18 p=2 перехід з решітки (289 CX) на повну зв'язність (144 CX)
зберігає 40% безшумного значення замість 24%. Проте вже безшумний QAOA на 18–21 кубітах малий (1.2% / 0.07%),
і найкращий шумний варіант — L18 p=2 all при 1% — дає 0.47%, нижче порога 0.5% (хоч і в ~50× вище baseline).
L21 має 0.02% при 1%, для L28 оцінка F при 1% — 0.007–0.09. Тож запуск холодного QAOA для L18/L21 на Forte
($0.08/shot) не виправданий: очікуваний сигнал на рівні кількох shots з тисячі. Великі ЦОД на залізі показуємо
через алгоритм 2 (QAOA лише над новими ВМ, 7–10 кубітів, `placement_new.py`), де глибина схеми лишається малою.

| CP-SAT | period:3 | 4.78 ± 0.52 | 95.6 ± 10.3 | 11.5 ± 3.1 | 53.5 ± 14.9 | 6 |

Висновок: перерозподіл із членом міграцій тримає кількість серверів на нижній межі (3.94 — як повна переукладка)
при в 4.5× менших міграціях і 4.7× меншому мігрованому навантаженні. BRKGA mu=1 майже досягає точного еталону
за серверами (79.0 проти 78.9 ФС·кроків), але мігрує на ~10% більше ВМ і на ~23% більше навантаження — це запас,
який точний (або квантовий) алгоритм 1 міг би забрати. Рідший перерозподіл (поріг 0.6 або кожні 3 кроки)
зменшує міграції ще в ≈2.6×, але коштує +17–21% ФС·кроків, тобто для енергії вигідніше консолідувати щокроку
з μ ≈ 1. CP-SAT з лімітом 10 с не завжди доводить оптимальність на кроці і з 8 потоками недетермінований
(розкид ±1–2 міграції між повторними прогонами).

**Старе slack-кодування** (`qaoa.py`, 16 кубітів) не концентрує розподіл на допустимих розв'язках
(11.9% допустимих при baseline 12.5%); «QAOA знайшов оптимум» у ранніх звітах був артефактом відбору з тисяч
shots. Виправлено переходом на slack-free кодування.

## Наступні кроки
- BRKGA з міграціями: декодер має для мігруючих ВМ спершу пробувати вже активні ФС (зараз First Fit
  за індексом робить частину оптимумів недосяжними — див. «Міграції: статистика по випадкових x0»).
- Алгоритм 2: розміщення нових ВМ на частково заповнені сервери (QAOA лише над новими ВМ — менше кубітів).
- Симуляція життєвого циклу ЦОД: прихід ВМ → розміщення → вимкнення частини → перерозподіл з міграціями.
- Контроль з випадковими кутами для інстансу C на Garnet; більший інстанс (18 кубітів) спершу в шумній симуляції.
